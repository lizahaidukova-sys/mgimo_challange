## 20.11.2026 — подготовка

### И1. Доступ к кабинету конкурса

| Поле | Значение |
|---|---|
| Задача | Войти в личный кабинет и забрать актуальное задание |
| Действие | Вход по логину из исходных данных, обход страниц номинаций |
| Результат | Задание «Вайб-кодинг» и «ИИ-проект» прочитаны; найдена форма отправки и её условия |
| Ошибка | Прямая ссылка на материалы партнёра отдавала HTML вместо PDF (нужна сессия) |
| Исправление | Запрос файла из контекста авторизованной страницы, затем сохранение PDF |
| Вывод | У частных файлов конкурса нельзя проверять доступность через `curl` без cookie |

### И2. Оценка сроков

| Поле | Значение |
|---|---|
| Задача | Понять, реально ли уложиться |
| Действие | Разбор критериев, оценка объёма по артефактам |
| Результат | Ядро — 7–9 ч, документ — 3–4 ч, деплой — 1 ч; итого 14–19 ч при ~50 ч запаса |
| Риск | Критерий «Масштаб ИИ» закрывается документом, а не кодом; без него максимум 3/10 |
| Решение | Промпты и скриншоты пишутся по ходу, а не восстанавливаются в конце |

## 20.11.2026 — реализация

### И4. Стек: отказ от метафреймворка

| Поле | Значение |
|---|---|
| Задача | Выбрать клиент и сервер так, чтобы проверки доступа были явными |
| Промпт | стадия 4, `docs/05-promptbook.md` |
| Первый вариант | ассистент собрал каркас на Next.js: серверные компоненты и server actions |
| Проблема | путь запроса спрятан; для проверки «чужой id недоступен» пришлось бы читать фреймворк, а не свой код |
| Решение | React + Vite на клиенте, Express на сервере: каждый маршрут виден целиком |
| Итог | 15 проверок доступа читаются без фреймворка и воспроизводятся одной командой |

### И5. Третья попытка «упростить доступ»

| Поле | Значение |
|---|---|
| Что просили | «покажи заявку по id» |
| Что получили | `SELECT * FROM requests WHERE id = ?` — без `user_id` |
| Как поймали | контракт `AGENTS.md`: id из запроса не является основанием доступа |
| Исправление | `WHERE id = ? AND user_id = ?`, чужой id → 404 |
| Проверка | `verify-idor.ts`: «студент А не видит чужую заявку» |

### И6. «Что изменилось» показывало пустоту

| Поле | Значение |
|---|---|
| Симптом | блок «Что изменилось» пуст при первом открытии, а после демонстрационного обновления страницы пустел снова |
| Причина | точка отсчёта хранилась в `last_seen_at` и сдвигалась при каждом заходе: скрытое состояние управляло видимым контентом |
| Первое исправление | убрали обновление при логине |
| Второй симптом | повторное открытие главной всё равно обнуляло список |
| Итоговое решение | колонка `last_seen_at` удалена; окно изменений фиксировано — последние трое суток |
| Побочный дефект | даты сравнивались строками; заменено на числовое сравнение |
| Почему так лучше | блок предсказуем для жюри и не зависит от того, сколько раз страницу открывали |

### И7. Оценки выглядели «выставленными только что»

| Поле | Значение |
|---|---|
| Симптом | в «Что изменилось» две оценки с временем «только что» |
| Причина | сид ставил всем записям `updated_at = now` |
| Исправление | у каждой оценки своя дата в прошлом; «новой» считается только свежая |

### И8. Перенос пары терял исходное время

| Поле | Значение |
|---|---|
| Симптом | повторное «перенесено» без изменения времени затирало исходное время |
| Причина | `previous_starts_at` перезаписывался текущим значением без проверки |
| Исправление | старое время сохраняется только если время действительно изменилось |
| Проверка | в API расписания у перенесённой пары есть `previous_starts_at` |

### И9. Срок заявки в нерабочий день

| Поле | Значение |
|---|---|
| Симптом | заявка, поданная в пятницу, получала срок в субботу |
| Причина | рабочие дни считались в локальной зоне сервера |
| Исправление | `server/time.ts`: границы суток, день недели и сборка времени — по Москве |
| Проверка | пятница 22:00 + 3 рабочих дня → среда 18:00 МСК |

### И10. Навигация на десктопе уезжала под футер

| Поле | Значение |
|---|---|
| Симптом | на скриншоте 1280 px горизонтальное меню оказалось внизу страницы |
| Причина | десктопное меню стояло после `<main>` |
| Исправление | меню перенесено под шапку, закреплено `sticky top-14` |
| Проверка | повторный скриншот десктопа |

### И11. Цели меньше 44 px

| Поле | Значение |
|---|---|
| Симптом | ссылки «Вся неделя», «Все», кнопка «Что закрыть» — 20–36 px по высоте |
| Как нашли | замер `getBoundingClientRect` по всем интерактивным элементам на 360 px |
| Исправление | `min-h-11` у ссылок и кнопок, карточка заявки — не ниже 44 px |
| Проверка | повторный замер: элементов ниже 44 px нет |

### И12. Мутация проходила с чужим Origin

| Поле | Значение |
|---|---|
| Симптом | проверка CSRF работала только при заданном `APP_ORIGIN` |
| Причина | при пустой переменной условие `origin && expected` всегда ложно |
| Исправление | при пустой переменной сравниваем Origin с фактическим хостом запроса |
| Проверка | `verify-idor.ts`: «мутация с чужим Origin отклоняется» → 403 |

### И13. Секрет сессии не использовался

| Поле | Значение |
|---|---|
| Симптом | `SESSION_SECRET` был в `.env`, но токен хешировался обычным SHA-256 |
| Риск | утечка файла базы позволяла бы проверить поддельные токены офлайн |
| Исправление | HMAC-SHA256 с секретом; в production без секрета сервер не стартует |
| Проверка | `verify:secrets`, вход после смены секрета |

### И15. Лимит попыток обходил перебор адресов

| Поле | Значение |
|---|---|
| Симптом | 12 запросов с неверным паролем для существующего адреса дали 429, а для несуществующего — 12 раз 401 |
| Причина | попытка записывалась только если пользователь найден |
| Риск | перебор базы адресов без ограничения |
| Исправление | попытка считается всегда; 11-я возвращает 429 |
| Проверка | 11 запросов на неизвестный адрес: десять 401, затем 429 |

### И16. Чистый клон не собирался на Node 24

| Поле | Значение |
|---|---|
| Симптом | `git clone` → `npm ci` падал на `better-sqlite3`: node-gyp не нашёл Visual Studio |
| Причина | нативный модуль: prebuilt под Node 24 нет, значит нужна локальная сборка |
| Почему это критично | жюри и любой новый человек не смогли бы запустить проект по README |
| Исправление | переход на встроенный `node:sqlite` (Node 22.5+): ни компилятора, ни node-gyp |
| Цена | API помечен экспериментальным; предупреждение в stderr подавлено флагом |
| Проверка | чистый клон: `npm ci` 9 с, `npm run seed`, `npm run build`, `npm start`, вход и главная — 200 |

### И14. Проверки портили демо-данные

| Поле | Значение |
|---|---|
| Симптом | `verify-idor.ts` работал на основной базе и добавлял тестовые заявки |
| Исправление | проверка поднимает сервер на временной базе `data/verify.db` и удаляет её после прогона |
| Ограничение | на Windows файл остаётся заблокированным до выхода процесса — добавлено ожидание |

### И17. Модалка не закрывалась с клавиатуры

| Поле | Значение |
|---|---|
| Симптом | «Правка пары» открывалась, но Escape не работал, фокус оставался на кнопке за диалогом |
| Как нашли | аудит доступности: ручной прогон Tab и Escape |
| Причина | диалог был просто `div` с `role="dialog"`, без обработки клавиш |
| Исправление | фокус входит в первое поле, Escape закрывает, фокус возвращается на кнопку-открывашку |
| Проверка | открытие: `focusedId = startsAt`; Escape: диалог скрыт, фокус на «Изменить» |

### И18. Табы обещали ARIA-поведение, которого не было

| Поле | Значение |
|---|---|
| Симптом | `role="tab"` + `aria-selected`, но стрелки не переключают и `tabindex` не настроен |
| Почему это дефект | роль обязывает к клавиатурной модели; её отсутствие хуже честных кнопок |
| Исправление | `role="group"` и `aria-pressed` — поведение совпадает с заявленным |
| Альтернатива | полная реализация tablist со стрелками — лишний код ради двух разделов |
